# sputnic-llc — файлообменник (Fullstack)

MVP файлообменника: загрузка файлов, асинхронная проверка на подозрительный
контент (Celery/Redis) и лента алертов. Бэкенд — FastAPI + SQLAlchemy
(asyncpg/psycopg) + PostgreSQL + Alembic; фронтенд — Next.js (App Router) +
react-bootstrap.

---

## Запуск (dev)

```bash
docker compose -f docker-compose.dev.yml up --build
docker exec -it backend alembic upgrade head
```

- Фронтенд: http://localhost:3000/ (также доступен по старому адресу http://localhost:3000/test)
- Бэкенд API / Swagger: http://localhost:8000/docs
- PostgreSQL с хоста: `localhost:5433` (`postgres` / `postgres`, база `test`)
- При первом запуске Postgres инициализируется сам (healthcheck'и настроены).

### Тесты

Бэкенд (не требует внешних сервисов — SQLite in-memory):

```bash
docker compose -f docker-compose.dev.yml run --rm backend python -m pytest
```

Фронтенд (Vitest + Testing Library):

## Что было сделано

### 1. Рефакторинг бэкенда (слои вместо «сервиса-швейцарского ножа»)

Было: один модуль `service.py` смешивал конфигурацию (чтение `os.environ` на
импорте, `mkdir`), движок БД, файловые операции, сессии, HTTP-исключения и
зависел от FastAPI (`UploadFile`, `HTTPException`); `tasks.py` создавал второй
движок и импортировал FastAPI-модуль в Celery.

Стало:

```
backend/src/
├── config.py      # Settings (pydantic-settings), сборка DSN
├── db.py          # фабрики async/sync engine + session
├── errors.py      # доменные ошибки (без HTTP)
├── models.py      # ORM (StoredFile, Alert; FK с ON DELETE CASCADE)
├── schemas.py     # Pydantic DTO + валидация
├── storage.py     # потоковая запись с лимитом, атомарный commit
├── scanner.py     # чистые правила скана + потоковые счётчики метаданных
├── services.py    # прикладной слой (use-cases файлов и алертов)
├── main.py        # фабрика FastAPI-приложения (DI через app.state)
├── api/           # роуты и зависимости (тонкий слой)
└── worker/        # Celery + sync-пайплайн (scan -> metadata -> alert)
```

Публичный API-контракт не изменился (пути, методы, поля, статусы).

### 2. Исправленные баги

| Баг | Было | Стало |
| --- | ---- | ----- |
| Несовпадение порта Postgres | бэкенд ходил на `backend-db:5433`, а Postgres слушает 5432 → `alembic`/запросы падали | порт внутри сети 5432; наружу `5433:5432`; healthcheck'и |
| DELETE файла с алертами | физический файл удалялся до удаления строки, FK-нарушение → HTTP 500 + «сирота» | `ON DELETE CASCADE` + удаление строки первым → 204 |
| Чтение файла целиком в память | `upload.read()` и повторное `read_text`/`read_bytes` в метаданных, без лимитов | потоковая запись с лимитом (413), потоковые счётчики |
| Зависание статуса `processing` | исключение в задаче оставляло файл в `processing` навсегда | `failed` + critical-алерт |
| Падение `.delay()` | Redis недоступен → 500, хотя файл уже создан | `enqueue_scan` запускает inline-обработку в фоне |
| Доверие MIME клиенту | `.pdf` с подделанным `Content-Type` проходил проверку | проверка magic-байтов (`%PDF`) |
| `title` > 255 символов | DB-ошибка → 500 | Pydantic-валидация → 422 |
| `Dockerfile` фронтенда | `COPY .env.production` несуществующего файла → сборка падала | убран |
| Redis/Layout: `depends_on` без healthcheck, `favicon`/хардкод URL | гонки при старте, битые ссылки | исправлено в compose/фронте |

### 3. «Неочевидная» оптимизация

- **Потоковая обработка с ограниченной памятью**: файл больше не читается
  целиком ни при загрузке (чанки 1 МБ + атомарный os.replace), ни при
  извлечении метаданных (счётчики строк/символов и approx_page_count по
  чанкам). Для PDF учтён «подводный камень» — токен /Type /Page, пересекающий
  границу чанка, считается корректно (перенос хвоста). Подробное обоснование
  и компромиссы — в разделе 3.1.
- **Один конфиг и отсутствие дублей движков**: убран event-loop хак в Celery;
  у воркера один ленивый sync-движок (psycopg), у API — async (asyncpg).

### 3.1 Потоковая обработка — reasoning (зачем читать файл частями)

**Проблема исходного кода.** Загрузка и обработка файлов читали данные целиком
в память, причём дважды за жизненный цикл файла:

```python
# 1) веб-процесс: весь файл в RAM, только потом на диск
content = await upload_file.read()
stored_path.write_bytes(content)

# 2) celery-worker: ещё одно полное чтение для метаданных
content = stored_path.read_text(...)   # или read_bytes() для PDF
```

Следствия:

- потребление памяти O(размер файла): при 500 МБ файле процесс держит 500 МБ в RAM;
- **двойной пик**: файл читается целиком в API, а затем ещё раз целиком в worker;
- веб-процесс один и асинхронный: одна «тяжёлая» загрузка роняет память всего
  сервиса (OOM / отказ других запросов), это же вектор DoS;
- лимит размера проверялся уже **после** чтения — файл успевал полностью
  попасть и в память, и (при ошибке БД) остаться «сиротой» на диске;
- падение процесса в середине `write_bytes` оставляло частично записанный файл.

**Решение.** Чтение/запись потоком порциями фиксированного размера (чанк по
умолчанию 1 МБ):

```python
# upload: routes -> storage.write_temp
while chunk := await upload.read(chunk_size):   # 1 МБ
    size += len(chunk)
    await asyncio.to_thread(fh.write, chunk)     # на диск, не в память

# metadata: scanner.extract_* — те же чанки, только счётчики
while chunk := fh.read(_SCAN_CHUNK_SIZE):
    char_count += len(decoded)
    ...
```

Память в любой момент ограничена одним чанком + счётчиками, то есть O(1)
относительно размера файла. Содержимое обрабатывается полностью — «обрезается»
только буфер, а не данные.

**Почему это важно именно для этого приложения:**

1. uvicorn-процесс один на всех пользователей — буферизация больших файлов
   в RAM превращается в отказ всего API;
2. файл физически читается минимум дважды (upload и метаданные в worker),
   держать его целиком в памяти оба раза — двойной пик;
3. лимит (`max_upload_size`, по умолчанию 512 МБ) теперь проверяется **в
   процессе чтения**: превышение → `413` без накопления файла и без «хвостов»
   на диске (temp-файл удаляется);
4. счётчики метаданных (`line_count`, `char_count`, `approx_page_count`) не
   требуют содержимого в памяти — только инкрементальную арифметику;
5. запись атомарна: данные идут во временный файл `.upload-<uuid>.part`, а в
   финальное имя переносятся `os.replace` — файл в хранилище либо появляется
   целиком, либо не появляется вовсе (нет «обрубков» при падении/ошибке БД).

**Подводный камень границы чанка.** Если считать вхождения токена по чанкам
независимо, токен, разрезанный границей между чанками, теряется:

```
...ч<N> |/Type /Pa|ge...ч<N+1>
```

Поэтому каждый следующий чанк склеивается с хвостом предыдущего размером
`len(токена) − 1` байт (перенос хвоста / carry). Наивная потоковая реализация
дала бы другой результат, чем чтение файла целиком, — на это есть отдельный
тест `test_pdf_metadata_token_crosses_chunk_boundary`, который ужимает чанк до
7 байт и сверяет результат с `content.count(token)`.

**Эквивалентность бизнес-логике.** Результаты совпадают с полнофайловым
чтением: размер файла, `line_count`, `char_count`, `approx_page_count`
идентичны (проверяется юнит-тестами, включая тест на границу чанка). Статусы
обработки (`uploaded -> processing -> processed/failed`), правила скана и
формат алертов не менялись.

**Компромиссы.** Потоковая обработка добавляет накладные расходы на системные
вызовы (больше операций чтения/записи) и сложность кода. Запись на диск
выполняется через `asyncio.to_thread`, чтобы не блокировать event loop. Для
очень маленьких файлов выигрыш в памяти несущественен, но и потерь нет;
чанк в 1 МБ выбран как баланс между количеством syscall и размером буфера.
Если бы файлы были гарантированно маленькими (≤ пары МБ), достаточно было бы
простого `read()` — поэтому это «неочевидная» оптимизация: её ценность
проявляется на больших файлах и под нагрузкой.
